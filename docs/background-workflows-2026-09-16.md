# 第二轮：后台任务、待确认建议和检索同步

基于 `codex/workflow-reliability` 的 `06f37b3`，本轮分支为 `codex/background-workflows`。沿用现有 Ant Design 组件和视觉风格。

## 已实现

### 总结生成

- 新增持久化任务队列。提交后立即返回 202，页面每 5 秒读取任务状态，关闭页面不影响执行。排队、执行阶段、完成、失败及重试状态可见；界面展示最近 30 项任务。
- 手动入口、旧生成 URL 和每日/每周/每月/每年定时入口统一入队。同一用户、同一周期正在处理的请求会合并；不同生成批次保留为独立报告。
- 可选择历史日期和日/周/月/年，预览北京时间统计范围、记录数和时长。周以周一开始；范围以开始时间包含、结束时间排除的规则选择日记。
- 生成不再先删除旧总结。模型失败或建议 JSON 校验失败时保留旧报告；任务失败可重试。新报告使用任务 ID，恢复执行不会重复插入报告。
- 输入日记快照保存在未完成任务中；长周期资料分段整理，避免旧模型客户端直接截断超过 20,000 字符的输入。成功后移除任务里的原文快照和临时正文，报告保留来源 ID 和内容哈希。
- 查看报告时检查来源新增、修改、删除和日期变化，提示报告是否过期。新报告 HTML 从已保存正文转义生成，避免重新读取现在的日记改变旧报告。
- 沿用个人提示词和默认模板，填充工作画像及待办统计。待办数量明确是生成时状态，不冒充历史期末快照。

### AI 建议

- 生成建议进入 `TodoSuggestion`，没有确认前不会创建正式待办。
- 用户可修改内容、优先级、截止日期后确认，也可忽略。模型不替用户确定正式截止日期。
- 确认使用预分配的待办 ID；重复/并发确认只创建一条记录。关联日记再次按用户和未删除状态校验。
- 新建议支持多条来源日记，兼容字段 `relatedDiary` 保留第一条来源；不覆盖旧日记里的单个 `relatedTodo` 指针。旧日记与待办的缓存字段尚未全量迁移。
- 待办删除改为软删除，避免已接受的建议再次创建同一待办。清理永久删除记录时清除相关来源引用。
- JSON 和 ZIP 导出包含建议；JSON 恢复重映射建议、日记、总结、待办关联，兼容不含建议的旧备份。ZIP 正式恢复仍未开放，保留原来的仅预检行为。

### 检索与 Dify

- 移除日记保存请求中的外部同步等待。后台每 60 秒扫描持久化日记版本，覆盖网页、导入、公开 API、恢复备份等写入路径；失败不会伪装为日记保存失败。
- `DiarySync` 保存每条记录的同步版本和 Dify 映射。硬删除和备份替换前保留映射，让后台能清理远端文档和向量。
- PostgreSQL 在事务中完整替换单篇日记全部切片，写入失败回滚；使用事务级锁协调同篇写入。缩短或删除日记不会残留可用旧片段。
- 只读核对了线上表结构：`chunk_id` 为 varchar(50)，`embedding` 为 vector(4096)。新切片使用短哈希，兼容原字段长度；模型维度不匹配会明确报错，不自动修改表或混用向量。线上部署需保留匹配的 4096 维嵌入配置；256 维基础哈希不能直接写入该表。
- 问答仅检索当前用户、未删除、内容版本和嵌入配置一致的资料，返回模型前再次核验。指定日期无结果时不再回退到所有日期。
- 配置了外部 Embedding 后调用失败会报错重试，不再偷偷换成本地哈希向量。没有外部密钥时仍保留原有基础哈希匹配。
- Dify 用稳定的用户/日记名称查找文档，恢复丢失响应的创建请求；处理重复文档和删除 404。提交后等待 `indexing_status=completed`，重试未完成索引时不重复提交正文。
- Dify 同步接口改为队列入口，移除打印数据集密钥的日志。目标知识库由服务器配置，不接受普通请求指定任意数据集。
- Dify 文档列表使用[官方文档列表接口](https://docs.dify.ai/api-reference/文档/获取知识库的文档列表)的分页、名称筛选及索引状态字段。

## 数据与并发边界

- 新增 `BackgroundJob`、`TodoSuggestion`、`DiarySync` 集合；用户增加 `dataGeneration` / `workflowWriteVersion`，Todo 增加来源字段。没有改写生产历史数据。
- 队列通过 Mongo 原子认领、90 秒租约和 20 秒心跳恢复中断任务。自动尝试最多 3 次，之后由用户检查配置并手动重试。
- 总结和索引各有一个处理循环。索引任务按用户/目标合并，一个大用户的同步可能让后续同步等待。
- 独立 MongoDB 支持新队列。JSON 替换恢复仍要求副本集/分片集群；没有降低这一保护。
- 副本集上，总结落库和建议确认与备份恢复通过用户文档事务写入协调。恢复递增数据代次，恢复前未完成的生成任务无法写回旧数据。
- Mongo 与 Dify 不存在跨系统事务。同步是最终一致：自动扫描有最长约一分钟延迟，Dify 自身索引还需要时间。服务端宕机、超时和远端配置错误以任务状态反馈；不宣称跨系统严格一次执行。
- Dify 全局知识库仍由服务端管理员管理，本轮没有改造 Dify 自身的账号/知识库隔离，也未清理旧版本可能遗留的、没有日记映射的聚合文档。
- 旧 `summaryController` 的历史生成实现仍留在文件内，但现行路由和定时任务不再调用它们。后续可在移除旧调用方之后继续拆分/删除。

- 覆盖：并发入队、失败保留旧报告、来源变更、待确认建议、并发确认、跨用户访问、租约恢复、备份后任务失效、建议备份恢复、向量缩短/删除/回滚、空日期范围、过期向量过滤、Dify 丢失响应恢复及等待索引。
- 正式 `server.js` 在独立测试数据库启动，API 根路由返回 200。
- 前端 `npm run build` 通过；保留已有的 ESLint、Browserslist 和构建包体积警告。
- 浏览器使用合成账号、合成日记和固定模型响应，验证周期预览、后台完成、报告查看、建议编辑确认及待办列表展示。没有调用生产模型或向真实 Dify 写入测试资料。

## 发布状态

本轮仅提交并推送功能分支，不合并 master，不替换生产容器，不迁移生产 MongoDB。上线前需先备份 MongoDB、PostgreSQL、私有报告文件与配置；首次启动会逐步重建历史检索版本，可从同步任务查看进度。

回滚应用代码时保留新增集合。回滚不会自动撤销用户已确认创建的待办。生产升级、旧关系字段迁移和最终视觉方案单独处理。
